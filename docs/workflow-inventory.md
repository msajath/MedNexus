# MedNexus workflow inventory

23 October 2026. Inventory of implemented source, not a claim of production verification. Actual role enum is `patient`, `doctor`, `admin`. Backend route handlers are inline in `backend/routes/*.js`; reusable services are under `backend/utils`, with authentication, authorization, validation and availability middleware under `backend/middleware`. There is no separate controllers directory. Browser checks use real APIs and disposable localhost MongoDB; UI-contract tests are identified separately.

## Existing capability limits and coverage gaps

- There is no refresh-token endpoint. Sessions use an HttpOnly JWT cookie; expired users reauthenticate. Remember-me persistence options were not implemented, so the inert checkbox was removed while preserving the current session policy.
- Messaging is a recipient inbox/read implementation. No compose/send/reply endpoint exists, and booking/leave handlers do not create notifications. Do not label doctor-patient composition or notification delivery as passing.
- Doctor clinical authoring/retrieval has real API authorization tests but no frontend editor/viewer. That UI capability remains unavailable; a seeded inbox message or API fixture is not proof of that interface.
- Doctors cannot reschedule appointments; that implemented mutation belongs to patients. Availability removal is disabling weekdays, not a DELETE endpoint.
- Payments are manually confirmed receipts, not a payment gateway. Full refunds are tracked state transitions; partial refunds, actual fund movement and printable receipt export are not implemented or claimed.
- Operations reports are downloaded JSON snapshots generated in the browser, not CSV/PDF or a report-generation API. Downloaded contents are verified, not just selectors/filenames.
- Real SMTP provider delivery, production roles/network/backups, provider deployment configuration and production write workflows cannot be certified by localhost QA. Synthetic data never entered production medibook.
- Previous UI mocks and page-visit tests did not cover real persistence, SMTP reset, ambiguous receipt retries, stale leave previews, exact file bytes, historical fee snapshots or all unhandled navigation exceptions. The expanded scenarios specifically cover those gaps; see final report for execution status.

## API/source structure

All protected routers use auth middleware and explicit role/ownership checks. Schemas live in `backend/models`: User, Doctor, Appointment, Availability, DoctorLeave, Payment, MedicalRecord, Message, ContactMessage. Their writes use allowlisted validated fields; clinical and financial records have separate read permissions. `frontend/src/context/AuthContext.jsx` owns authentication state; page hooks/state manage local form/read state; `frontend/src/config.js` centralizes cookie credentials, CSRF marker, read-only retries, deadlines and invalid-session notification. `frontend/vite.config.js` proxies local API calls; Vercel rewrites production `/api` to Render. Production startup validates JWT secret and MongoDB TLS/database selection before listening on PORT.
